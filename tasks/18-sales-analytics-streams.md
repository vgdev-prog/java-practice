# 23. Аналітика продажів (Stream API + лямбди)

> Фаза D — стандартна бібліотека: стріми, I/O, regex, час.

## Постановка

Над списком замовлень порахувати набір аналітичних показників **виключно через Stream API**, без ручних циклів із мутацією зовнішнього стану. Кожен показник — окремий декларативний пайплайн.

## Сутності та відповідальність

- **Замовлення** — незмінний носій: клієнт, категорія, сума, дата.
- **Аналізатор** — набір методів, кожен повертає свій показник одним стрім-пайплайном:
  - сума продажів по кожній категорії (групування);
  - середній чек;
  - топ-клієнт за сумою покупок;
  - розбиття замовлень на «дорогі / дешеві» за порогом;
  - кількість замовлень по кожному клієнту;
  - перелік унікальних категорій, відсортований за алфавітом.
- За потреби — власні або стандартні функціональні інтерфейси (`Predicate`, `Function`) для параметризації фільтрів.

## Поведінка / вимоги

- Жодного `for` із накопиченням у зовнішній змінній — стріми для **трансформацій**, не для побічних ефектів (oop.md §9).
- Групування — через `Collectors.groupingBy`; розбиття за умовою — через `partitioningBy`; підсумки — через `reduce` / `summarizing*`.
- Лямбди й method references замість анонімних класів, де доречно.
- Гроші — на `BigDecimal`.
- Методи, що «можуть не повернути значення» (топ-клієнт на порожньому списку) → `Optional`.

## Що тренує

Stream API в глибину (`map`, `filter`, `collect`, `groupingBy`, `partitioningBy`, `reduce`, `summarizing`), лямбди, функціональні інтерфейси, `Optional` у комбінації зі стрімами.

## Acceptance criteria

- Кожен показник реалізований одним стрім-пайплайном, без зовнішньої мутації.
- Групування й розбиття — через відповідні колектори.
- Топ-клієнт на порожньому вході → порожній `Optional`, не `null` і не виняток.

## Очікувана поведінка (приклад)

```
sumByCategory()  → {ELECTRONICS=4200, BOOKS=350, FOOD=180}
averageCheck()   → 257.50
topClient()      → Optional[Olena]
partition(>1000) → {true=[...дорогі...], false=[...дешеві...]}
```
