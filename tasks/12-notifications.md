# 13. Система сповіщень

> Фаза B — інтерфейси, абстракції, поліморфізм.

## Постановка

Сервіс розсилає одне повідомлення користувачу одразу кількома каналами: email, SMS, push. Реалізації каналів незалежні. Сервіс не знає про конкретні канали — отримує їх список ззовні (як у Spring через DI).

## Сутності та відповідальність

- **Користувач** — незмінний носій: ідентифікатор, email, телефон, push-токен.
- **Контракт каналу сповіщення** — інтерфейс із одним методом «надіслати користувачу повідомлення».
- **Конкретні канали** — email (заглушка SMTP), SMS (заглушка HTTP-API), push (заглушка Firebase). Кожен реалізує контракт по-своєму.
- **Сервіс сповіщень** — отримує список каналів **через конструктор**, зберігає його незмінною копією. Метод розсилки проходить усіма каналами й шле повідомлення в кожен.

## Поведінка / вимоги

- Сервіс залежить від списку **контрактів каналу**, а не від конкретних реалізацій (Dependency Injection).
- Новий канал (наприклад, Telegram) додається без зміни сервісу (Open/Closed).
- Поле зі списком каналів — `List.copyOf(...)`, незмінне (зовнішній код не зможе підмінити канали після створення сервісу).

## Що тренує

Dependency Injection через конструктор (точно як у Spring), Open/Closed, захист внутрішнього списку незмінною копією.

## Acceptance criteria

- Сервіс приймає список контрактів каналу, а не конкретні канали.
- Список каналів зберігається як `List.copyOf(...)` — незмінний.
- Розсилка викликає всі канали по черзі.
