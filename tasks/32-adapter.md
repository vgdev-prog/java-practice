# 32. Адаптер стороннього сервісу (Adapter)

> Фаза F — патерни проектування (Gang of Four). Структурний.

## Постановка

Інтегрувати сторонню бібліотеку, інтерфейс якої **не збігається** з тим, що очікує наш код. Замість переписування — обгорнути її адаптером, що приводить чужий інтерфейс до нашого контракту.

## Сутності та відповідальність

- **Наш контракт** — інтерфейс, який очікує наш код (наприклад, `PaymentGateway` з методом `charge(amount, currency)`).
- **Стороння система (adaptee)** — клас із «чужим» інтерфейсом, який ми **не можемо змінити** (наприклад, `LegacyBillingApi` з методом `doPayment(cents, "USD", token)`).
- **Адаптер** — реалізує наш контракт, усередині тримає сторонній обʼєкт і **перекладає** виклики: конвертує параметри (гривні→центи, наш enum валюти → їх рядок), мапить результат і помилки.
- **Клієнт** — працює лише з нашим контрактом, про сторонній API не знає.

## Поведінка / вимоги

- Адаптер реалізує **наш** інтерфейс, делегуючи роботу сторонньому обʼєкту (композиція, не наслідування від чужого класу).
- Перетворення даних і помилок — відповідальність адаптера; клієнт нічого не конвертує.
- Заміна сторонньої системи на іншу = новий адаптер, клієнт не змінюється.

## Що тренує

Adapter: узгодження несумісних інтерфейсів, композицію поверх чужого коду, ізоляцію залежності від зовнішнього API.

## Acceptance criteria

- Адаптер реалізує наш контракт і всередині делегує сторонньому обʼєкту.
- Клієнт ніде не звертається до стороннього API напряму.
- Конвертація параметрів/результату/помилок інкапсульована в адаптері.
