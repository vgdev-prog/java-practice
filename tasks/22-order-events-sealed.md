# 24. Події замовлення (sealed + pattern matching)

> Фаза E — сучасна Java та великий домен.

## Постановка

Змоделювати замкнену (sealed) ієрархію подій замовлення й обробляти їх через `switch`-вираз із pattern matching — **замість** ланцюга `instanceof`. Компілятор має гарантувати, що оброблені всі види подій.

## Сутності та відповідальність

- **Подія** — `sealed`-інтерфейс, який **явно дозволяє** (`permits`) фіксований перелік реалізацій.
- **Конкретні події** — кожна `record`, що реалізує інтерфейс:
  - *Створено* — номер замовлення, момент;
  - *Оплачено* — сума, спосіб оплати;
  - *Відправлено* — трек-номер, перевізник;
  - *Скасовано* — причина.
- **Обробник** — приймає подію й через `switch`-вираз із pattern matching повертає опис / наступну дію. Використовує **record-патерни** (розбір полів прямо в гілці) і за потреби **guarded patterns** (`when`).

## Поведінка / вимоги

- Обробка — `switch`-вираз із pattern matching, **без жодного `instanceof`-ланцюга**.
- `switch` **без гілки `default`**: завдяки `sealed` компілятор сам перевіряє вичерпність — усі дозволені типи мають бути покриті.
- `when`-умови для розрізнення кейсів усередині одного типу (наприклад, оплата більша/менша за поріг).

## Trade-off (навчальна суть)

Це **протилежний підхід** до задачі 8 (платежі) і 18 (банкомат), де поліморфізм робив систему **відкритою** (новий тип — без змін у коді). Тут навпаки: додавання нової події **свідомо ламає** компіляцію `switch`, і це добре — компілятор покаже всі місця, які треба оновити. Закрита множина варіантів + вичерпний розбір.

## Що тренує

`sealed`-ієрархії, `switch`-вирази, pattern matching, record-патерни, guarded patterns, перевірку вичерпності компілятором.

## Acceptance criteria

- Ієрархія подій `sealed` з явним `permits`.
- Обробка через `switch` pattern matching без `default` і без `instanceof`.
- Додавання нової події викликає **помилку компіляції** у `switch` (доказ вичерпності).
